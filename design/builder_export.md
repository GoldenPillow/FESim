## 0-a. ★방향 (2026-09-07 사용자 지시 — 이전 가정을 대체한다)

> *"사이트로 유저를 유도하는것은 현시점에서는 중요하지 않음. 가장중요한것. 정보를 잘 보여주는것.
> 깔끔한 UI. 손실없는 해상도."*
> *"cf로 본격적인 유저유치는 처음이라 사용자의 자원소모우려가 있었으나. 이것을 판단해보고
> 에셋으로인한 소모가 미미하다면 직접링크도 허용"*

이 지시가 설계 축을 바꾼다:

| | 종전 가정 | ★확정된 우선순위 |
|---|---|---|
| 1순위 | 전 채널 도달·유입 | **판독성 · 깔끔한 UI · 무손실 해상도** |
| 코드 병기(복원 경로) | 주 설계 요소 | **후순위** — 유입 축이다. 단 "이미지가 낡는다"의 해법으로서의 가치는 남음 |
| 핫링크 | 회피 대상(서버 종속·CF 부하) | **조건부 허용** — 에셋 소모가 미미함이 수치로 확인되면 |

★**핫링크 허용이 여는 것**: 우리 도메인 이미지를 게시판에 `<img src>`로 걸면 게시판이 **재인코딩하지 않는다**
⇒ 디시 자동 리사이징을 **원천 우회**한다. 최우선 요구(무손실 해상도)를 정면으로 푸는 유일한 수단이다.
☠대가 = 게시물이 우리 주소에 영구 종속(채널 격하 시 손상) + §4-3 CF 경로 조치가 **선행 필수**.

★**사용자 실기 관측(정본 — 판독·문서보다 앞선다)**: *"현시스템을 캡쳐후 올렸을때 자동리사이징으로 흐릿한 현상"*
= 화면 캡처를 디시에 올리면 글자가 뭉갠다. **이 현상을 이기는 것이 이 피쳐의 1번 문제다.**

## 0-b. ★UI 확정 (2026-09-07 사용자 지시 — §5 미결 Q1·Q2를 종결시킨다)

> *"html과 이미지다운로드 별개로 준비하고 공유는 대중적인 화살표 아이콘을 찾아서 부착.
> 엔트리 목록의 우측 상단에 배치. (아이콘) Share 형태의 버튼. 누를시 팝업 기본 세트는 디스코드 HTML소스.
> HTML이 범용성이 있으니 순서는 먼저. HTML의 경우 가로 900으로 지정 원형폼을 유지하는가 사용자가 결과를 보고 재검증.
> 디코옆에 다운로드 버튼. 쉐어의 기준은 현재 엔트리에 포함된 부분."*

| 항목 | 확정 |
|---|---|
| 버튼 | **`(화살표 아이콘) Share`** — 유튜브식 공유 화살표. ☠상표·서비스 로고 금지(순수 기하 아이콘) |
| 위치 | **엔트리 목록의 우측 상단** (프리셋 상단바가 아니라 표 쪽) |
| 팝업 | 원형 아이콘 행(유튜브 공유 다이얼로그 형식). 세트 = **[HTML] [Discord] [다운로드]** |
| 순서 | ★**HTML이 1순위** — 범용성이 높다 |
| HTML | **가로 900px 고정**(디시 PC 본문 컨테이너와 일치). 원본 폼 유지 여부는 ☠**사용자가 결과를 보고 재검증** |
| Discord | 표·HTML이 전부 증발하는 채널이므로 **이미지를 클립보드로** |
| 다운로드 | **이미지 파일 저장** — 디코 버튼 옆 |
| ★이미지 폭 | **840px 고정**(2026-09-07 사용자 확정). 근거 = 디시 기본 리사이즈 폭 850이 **경계값**이라 *"원본이 더 작을 경우 원본 크기가 유지됩니다"*에 해당하려면 **엄격히 작아야** 한다. 840이면 리사이즈 분기를 아예 안 타므로 1px 괘선까지 무손상이고, PC 본문 900px 안에 확대 없이 들어간다. ☠HTML(900)과 다른 값인 것은 의도다 — 별개 산출물이고 제약이 다르다 |
| ★범위 | **현재 엔트리(잠금)에 포함된 것만.** 대기 목록은 대상이 아니다 |

⇒ **§5 Q1 = "PNG + HTML 둘 다"로 결정됨**(둘을 별개 산출물로 준비) · **Q2 = "HTML 갈래를 만든다"로 결정됨**.
남은 미결 = 아이콘 실체(핫링크 vs 텍스트) · 이미지 폭 · Q3(호스팅) · Q4(코드 병기 — 유입 후순위라 보류).

### 2-1a. ★디시 "흐릿함"의 기전 — 규명 완료 (2026-09-07)

사용자 관측(*"캡쳐후 올렸을때 자동리사이징으로 흐릿"*)의 정확한 원인. 근거 = 로컬 캐시 692건 전수 파싱 + 에디터 소스.

**(1) 업로드 시 서버가 파생본 4종을 만들고, 본문에는 축소본만 박힌다**
```js
// dc_editor_common.js — imageUploader()
// 응답: file.url(원본) / file.web__url / file.web2__url / file._s_url(썸네일)
if (file.web__url) imgurl = file.web__url;   // ★본문에 들어가는 건 "web" 파생본
```
원본은 `originalurl`로만 남아 **클릭 팝업 전용**이 된다.

**(2) 리사이즈 폭의 정본 — 모바일 글쓰기 설정**
```
* 설정한 가로 크기보다 원본이 작을 경우 원본 크기가 유지됩니다.
  원본 크기(ori) / 480 / 640 / [x] 850 (기본값) / 1024      ← m_write.html
```
- 기준은 **가로 폭만**, 세로는 비율 유지. **원본이 더 작으면 그대로 둔다**(축소만, 확대 없음)
- ☠**PC 글쓰기에는 이 옵션이 없다**(히든필드 25개 전수에 `imgSize` 부재)
- 설정은 `localStorage["imgSizeSetting"]`에 남아 그 브라우저에서 계속 적용

**(3) 표시 폭** — PC 본문 컨테이너 `<div class="write_div" style="width:900px">` — **53/53 게시물 전부 900px**

**(4) 원본 도달 가능성** — PC는 `imgPop` 클릭 팝업이 붙은 이미지만(전체의 **27.5%**).
☠**모바일 열람자는 원본에 영영 못 닿는다** — 모바일 본문에 `viewimagePop` **0건**, 줌 뷰어가 축소본 URL을 그대로 확대한다.

⇒ **1600~1920px 캡처가 850px로 = 0.44~0.53배. 12px 글자가 5~6px이 되어 죽는다.** 이것이 흐릿함의 전부다.

### 2-1b. ★무손실 규격 — 로컬 실측으로 확정

| 실측 | 결과 |
|---|---|
| **축소 비율** | 1/2·1/3·1/4(정수 분모)만 **밝기 편차 0**. 0.8·0.75·0.71·0.67·0.625·0.57·0.4 **전부 파괴**. ★"0.7배는 죽는다"의 이유는 대비 손실이 아니라 **선마다 격자 위상이 달라 어떤 선은 진하고 어떤 선은 2px 회색으로 갈리는 편차**다 |
| **1px 괘선** | 정수배 축소여도 대비를 잃는다(200 → /2에서 176 = 88%). **100% 사는 유일한 경우 = 리사이즈가 아예 없을 때** |
| **글자 크기 하한** | 숫자(라틴) **11px 하한 / 12px 안전** · **한글 13px 하한 / 14px 안전**(한글은 자소가 겹쳐 획 하나가 사라지면 글자가 바뀐다). ☠**9~10px는 어떤 축소에서도 못 산다** — 화면 캡처가 흐려지는 원인의 대부분 |

## 4. CF 무료티어 — 산입되는가

### 4-1. 공식 문서 결론
> *"Requests to static assets are **free and unlimited**."* — Workers static-assets/billing

- `run_worker_first: true`(현행) = **모든 요청이 워커를 거친다** ⇒ 아이콘까지 10만 req/일에 산입
- 배열 + `!` 부정 패턴(`["/*","!/_astro/*","!/fe17/assets/*"]`) **문법 유효 · 부정 패턴 우선** ⇒ 워커 미경유 = 무료·무제한
- ☠**초과 시 정적 폴백이 없다**: `run_worker_first`에 걸린 경로는 쿼터 초과 시 **429**.
  지금 상태로 핫링크를 뿌리면 아이콘 트래픽이 **빌더 사이트 전체를 죽인다**
- CF 핫링크 보호(Scrape Shield)는 지원 확장자가 gif/ico/jpg/jpeg/png뿐 — ☠**webp 미지원**이라 우리 아이콘엔 적용 불가
- R2 무료 = 저장 10GB·Class A 100만·Class B 1000만/월·**egress 무료**

### 4-2. 채널별 "우리 서버가 몇 번 맞는가"
- 디스코드·페북·슬랙·카카오·X·레딧·네이버 = 크롤 1회 후 **각자 CDN 프록시** ⇒ 부하 낮음
- ☠**Discourse만 비프록시** — 열람마다 원서버 호출
- ★**쿼리스트링이 다르면 전 채널이 별개 URL로 재크롤** ⇒ 빌드마다 URL이 다르면 크롤 요청이 빌드 수만큼 발생

### 4-2a. ★☠지금 상태가 시한폭탄이다 (2026-09-07 계산)

| 고유 아이콘 URL 수 | 429가 시작되는 조회수 |

## 5. 미결 (질문 게이트) — ☠승인 전까지 아래가 전부 잠긴다

### Q1. 주 산출물 형식
**배경**: 디시 관행은 이미지 압도(표 1.1% vs 이미지 69%)이고 디코는 HTML을 통째로 버린다. 반면 이미지는
룰이 바뀌면 낡고 재편집·재계산이 불가능하다(우리 프로젝트는 **엔진 피델리티가 계속 오르는 구간**이다).

- A) **PNG 카드 우선 + 빌드 코드 병기** (권장) — 디시·디코 양쪽이 통과하는 유일한 형식. 코드를 카드에 인쇄해
  이미지가 스샷으로 재유통돼도 원본 복귀 경로가 산다
- B) PNG 단독 — 가장 단순하나 산출물이 낡으면 되돌릴 길이 없다
- C) HTML 우선 — 디코가 빠지고(최우선 채널 하나 상실) 디시도 관행 밖이다
- D) 코드(텍스트) 단독 — pobb.in 형. 가장 싸고 안 낡지만 **게시판에서 아무것도 안 보인다**

**권장 이유**: 벤치마크에서 우리와 가장 유사한 도메인(원신 Enka — 스탯+장비+아이콘 다수)의 한국 게시판 채택
형식이 **PNG 카드**였고, 안 낡는 산출물을 원하는 요구는 **코드 병기**로 동시에 만족된다(동물의 숲 Design ID 패턴).
**안 정하면**: 렌더러 설계·직렬화 코덱·CF 경로 조치의 우선순위가 전부 미정으로 남는다.

### Q2. HTML 갈래를 만들 것인가, 만든다면 아이콘은
**배경**: 인라인 style이 사는 곳은 디시·아카·루리웹·인벤·에펨 5곳. data URI는 디시 예산상 **배제 확정**(§2-1).
남는 선택은 핫링크뿐이고, 핫링크는 게시물을 builder-engage 주소에 영구 종속시킨다.

- A) **HTML 갈래를 만들지 않는다** (권장 — Q1이 A/B일 때)
- B) 만들되 아이콘 **핫링크** — §4-3 선행 필수 + 채널 격하 시 과거 게시물 손상
- C) 만들되 **아이콘 없는 텍스트 표** — 안 깨지지만 빌더의 정체성이 사라짐

**권장 이유**: 디시 관행 정량(표 1.1%)이 HTML 표 수요가 희박함을 보이고, 유지비(모바일 h3/hr 소멸·65,535 예산·PC 전용 작성)가 크다.
**안 정하면**: 마크업 생성기를 만들지 말지가 정해지지 않아 작업량이 2배로 벌어진 채 남는다.

### Q3. 이미지를 어디에 두는가
**배경**: 클립보드 PNG는 게시판이 자기 서버로 흡수하므로 우리 부하가 0이지만, **디코 링크 카드(og:image)를
만들려면 우리가 이미지를 호스팅**해야 한다. 그런데 우리 철학은 *"서버 자원을 쓰는 행위가 로그인 게이트 경계"*다.

- A) **호스팅 안 함 — 클립보드/다운로드만** (권장, v1) — 게이트 제로 유지, 신규 인프라 0, 디코는 PNG 첨부로 커버
- B) 클라이언트가 굽고 R2에 업로드 → 짧은 URL(og:image 겸용) — 디코 링크 카드가 열리지만 **로그인 게이트 신설**이 전제
- C) 빌드 타임 정적 생성 — 유저 빌드는 무한하므로 성립 불가

**권장 이유**: B는 M4(공유 킷·소셜 로그인)의 영역이고 지금 발현하지 않는다(전역 Deferral Rule).
A로 시작해도 카드에 인쇄한 코드가 **나중에 B로 확장할 접합면**을 남긴다.
**안 정하면**: R2·로그인·og 경로를 v1에 넣을지가 미정이라 §0의 뒤 항목이 전부 흔들린다.

### Q4. 링크에 빌드를 담는가 (서버 없는 공유)
**배경**: `BuilderSnapshot`은 순수 JSON이라 압축+base64url로 URL에 통째로 담을 수 있다(pobb.in·PoB 선례).
이러면 **서버 자원 0 · 로그인 0 · 링크 사망 0**이다. 다만 계획서 §10-2가 *"링크 공유는 로그인"*으로 적혀 있어
**확정 사항과의 경계 확인이 필요**하다(그 조항의 근거는 "서버 자원을 쓰는 행위"이고, URL 자체 완결은 서버 자원을 안 쓴다).

- A) **담는다 — 자기완결 URL**(권장) — 짧은 링크 발급(서버·로그인)과 **다른 축**으로 병존
- B) 안 담는다 — M4 짧은 링크까지 기다린다

**권장 이유**: 게이트 제로 철학의 문자 그대로의 확장이고, 지금 있는 것(프리셋 코덱)만으로 된다.
**안 정하면**: 코드 갈래의 그릇(URL이냐 텍스트 코드냐)이 안 정해져 코덱을 못 짠다.
☠**선행 실측** = 실제 12엔트리 프리셋의 압축 후 길이(§6-5). URL 길이 한계를 넘으면 A가 무너진다.

전 옵션을 통과하는 폭은 460 이하인데 판독성이 무너져 기각 ⇒ **내보내기 UI에 안내 한 줄**로 푼다
(*"디시 모바일 글쓰기 → 이미지 크기 = 원본 크기"*).

### (6) 구현 순서 (충돌 최소 — ☠UI를 먼저 만들지 말 것)
